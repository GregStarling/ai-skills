# Skill Audit skill — 2026-10-29

The October skill audit (PR 22, [results](skill-audit-results.md)) became a
skill of its own. The maintainer asked for a manually run skill that does two
jobs in one pass: audit a whole collection the way PR 22 did, and act as a
check on skills made by Anthropic's skill-creator, fixing what they get wrong.

## Design

- **One pass, no modes.** Scope defaults to every installed skill plus the
  repository's `skills/`. A skill fresh from skill-creator is checked because
  it is in scope, by the same rules as everything else.
- **Manual only, on both hosts.** `disable-model-invocation: true` in the
  frontmatter (Claude Code) and `policy.allow_implicit_invocation: false` in
  `agents/openai.yaml` (Codex). The packaging check now accepts that one extra
  frontmatter key.
- **Edit only what is ours.** `inventory.mjs` marks generated skills, synced
  or plugin-managed skills, and installed copies of a repository skill as
  report-only, so fixes land in the generator, upstream or the source repository.
- **Mechanical now, judgment after approval.** Reference hygiene is fixed during
  the pass. Descriptions, names, instructions and scripts become numbered
  proposals in AUDIT.md, and the skill stops for approval, as Phase 2 did.
- **Triggering is measured, not argued.** `trigger-eval.mjs` generalizes the
  runner used for PR 22: a throwaway project per session, only the chosen skill
  sets installed, environment stripped to `HOME PATH USER SHELL TMPDIR`. With no
  API key, sessions use the Claude Code login and count against subscription
  limits, not an API bill. Sessions stop at the first Skill call, and a usage
  limit stops the run and yields a partial report. Codex hosts report triggering
  as not run.
- **One lint.** `scripts/lint-skills.mjs` moved into the skill, lost its `yaml`
  dependency (a small frontmatter reader replaced it; it matched `yaml` on all
  112 installed, plugin-marketplace and repository skills), and still gates
  `scripts/verify/skills.mjs`.
  It now accepts several folders, finds nested skills, rejects XML tags in
  descriptions, and warns on descriptions with no exclusions.

## Why a check on skill-creator

Linting the installed skill-creator found its own SKILL.md body at 502 lines,
four long agent and reference files without a contents list, and a reference
named without a reason to read it. Its guidance differs from Anthropic's
best practices in ways that explain recurring problems: contents lists only past
300 lines, "pushy" descriptions with no voice rule or exclusions, and trigger
tests that register the description as a temporary command in the user's real
project and run `claude -p` with the full environment, so installed skills,
global instructions and any API key influence the result.
`references/review-rules.md` records the divergences; skill-creator itself is
reported, not edited.

## Validation

- `test/foundation/lint-skills.test.ts`: frontmatter reader, nested discovery,
  XML tags, exclusions warning, "use this skill whenever" as a when-clause,
  capitalised first person.
- `test/routing/skill-scripts.test.ts`: inventory status and shared triggers;
  trigger runner dry run, session scoring, early stop and API-key stripping,
  using a stand-in `claude`.
- Repository checks: `npm test`, `npm run typecheck`, `npm run build`,
  `node scripts/verify/skills.mjs`.
- Live trigger test (4 Opus sessions, Claude Code login, repository skills
  plus skill-audit installed): Focus fired 2/2 on its explicit prompt, and
  "Audit the skills in .claude/skills against best practices…" fired no skill
  2/2, so skill-audit does not load itself.
- Live `/skill-audit skills/` run (one headless Opus session, isolated
  environment) on a fixture with a skill-creator-style skill (pushy imperative
  description, 135-line reference without contents, vague and nested reference
  links), a competing changelog skill, and a generated skill. The session ran
  inventory and lint, made a snapshot and branch, applied exactly the three
  reference fixes (lint FAIL 6 to 2), left the generated skill untouched and
  reported it to its generator, identified the changelog collision, wrote
  AUDIT.md with six numbered before/after proposals and a 36-session trigger
  plan, and stopped at `SKILL AUDIT AWAITING APPROVAL`. Its installed copy
  predated the two lint fixes below, so the generated skill's "My" showed as a
  voice warning rather than a person failure. The approval half (apply and
  measure) was exercised by the trigger runner tests and the live trigger test,
  not in this session.

## Independent review

A fresh Opus review returned REPAIR with eleven findings, all fixed:
- Report-only detection now reads only explicit do-not-edit markers near the
  top, so prose like "files generated by protoc" no longer counts.
- Managed paths are anchored to host locations, and a Git plugin-layout
  repository stays editable.
- A skill installed in several places outside Git is reported until its source
  is in scope.
- Symlinked installs are deduplicated.
- The frontmatter reader handles a description starting on the next line and
  trailing comments.
- The trigger runner leaves errored and timed-out sessions unscored, reads
  short host results for usage limits, rewrites results after every session,
  cleans up on signals with a SIGKILL fallback, and exits 2 on missing folders.
- SKILL.md now covers project and plugin skills in the default scope, a
  per-root snapshot, before and after sets that differ only in the changed
  skills, and background execution of long trigger runs.
- The skill README no longer suggests plain-language invocation.

A second pass found four more problems, all fixed:
- A short answer from the model that mentioned rate limits could stop a run.
  Limit and login text is now read only from failed sessions (non-zero exit or
  an error result), and any failed session is unscored.
- Generated-skill markers now catch `DO NOT EDIT.` and `Do not edit;` and no
  longer match prose such as "ignoring auto-generated files".
- The template's example plan pointed `before` at the snapshot; it now points
  at an assembled flat folder.

## Limits

Collision candidates come from shared words and quoted triggers; the agent
still judges semantic overlap the word lists miss. Trigger tests need the
`claude` CLI. The 100-line contents rule and voice rules come from Anthropic's
published guidance; the trigger lessons come from three runs per case on this
collection, not a general benchmark.
