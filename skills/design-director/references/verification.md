# Verification and correction

Match proof to risk. Every visual change needs a real rendered capture and a
fresh independent critic. Interaction, uncertainty, and high-risk work add the
relevant states, viewports, keyboard/focus, reduced motion, errors/recovery, and
interaction evidence.

When decomposing work into tasks, bind `high_stakes` and `visual` proof to
every selected high-risk surface. Also bind `interaction` when the surface
operates or protects behavior; validate these bindings before execution.

## Evaluate

Pin the repository state, constitution revision/hash, capture manifest, surface
and state ids, viewports, interactions, screenshots, and configuration version.
Review every applicable floor and product clause.

Categorize each finding:

- `implementation_mismatch`: code/rendering does not implement a valid clause;
- `content_data_failure`: missing, misleading, unrealistic, or broken content/data;
- `constitutional_failure`: strong evidence shows the clause itself is wrong.

Emit `preserve` for the first two and correct the implementation or content.
When a host runtime provides a remediation channel, route those findings
through it. In standalone use, apply the corrections directly and keep the
resolution advisory. Route the third to an `amend` proposal; never force code to conform to
a disproved principle. There is intentionally no fifth “correction”
constitution resolution.

## Bounded loop

Batch findings into one correction pass, then run one independent confirmation
pass. Continue only when new evidence—not aesthetic restlessness—justifies it.
Recheck the final integrated state and all affected completed work after an
amendment.

Report clause coverage, dispositions, unresolved experimental clauses, current
revision/hash, and evidence references. Mechanical success is necessary where
applicable but never sufficient proof of product-design quality.
